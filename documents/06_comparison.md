# 06. RESTful vs RPC vs gRPC 비교 (초보자용)

## 1) 한 줄 요약

- **RESTful**: “자원”을 URL로 표현하고, 행동은 HTTP Method로 표현(웹 표준 친화적)
- **RPC**: “함수/메서드 호출” 중심(행동 중심 모델링이 자연스러움)
- **gRPC**: “고성능 RPC” + “.proto로 계약 정의 + 코드 생성”(타입 안정성/성능/스트리밍 강점)

---

## 2) 비교표(초보자 관점)

| 항목 | RESTful | RPC(일반) | gRPC |
|---|---|---|---|
| 사고방식 | 자원(Resource) 중심 | 행동/명령(Procedure) 중심 | 행동/메서드 중심 + 강한 계약 |
| 전송/프로토콜 | HTTP(주로 JSON) | 다양(HTTP/TCP 등) | HTTP/2 + Protobuf |
| 브라우저 친화성 | 매우 좋음 | 구현 방식에 따라 다름 | 기본은 불편(추가 구성 필요) |
| 타입 안정성 | 낮음~중간(JSON 스키마 필요) | 구현에 따라 다름 | 높음(.proto 기반) |
| 성능/효율 | 보통 | 다양 | 좋음(바이너리/HTTP2) |
| 디버깅 용이성 | 좋음(JSON/텍스트) | 보통 | 초반엔 어려울 수 있음 |
| 스트리밍 | 제한적(SSE/WebSocket 등 별도) | 구현에 따라 다름 | 강함(스트리밍 내장) |
| 학습 난이도 | 낮음~중간 | 중간 | 중간~높음(코드 생성/빌드 이해 필요) |

---

## 3) 언제 무엇을 쓰면 좋을까요? (상황별 추천)

### 3.1 RESTful 추천
- 외부 공개 API(개발자들이 쉽게 쓰게 하고 싶을 때)
- 브라우저/모바일에서 바로 호출해야 할 때
- 리소스 중심으로 모델링이 자연스러울 때(게시글/댓글/상품 등)

### 3.2 RPC 추천
- “명령/행동” 중심의 내부 API가 많을 때
  - 결제 승인, 재고 예약, 정산 처리 등
- 팀에서 REST 규칙보다 “메서드 계약” 중심으로 개발하고 싶을 때

### 3.3 gRPC 추천
- 내부 마이크로서비스 통신에서 성능/타입/계약이 중요할 때
- 스트리밍이 중요한 경우(실시간 피드, 게임, IoT 등)
- 여러 언어 팀이 같은 계약(.proto)으로 협업해야 할 때

## 4) 이 레포에서 제공할 “최소 실행 예제” 구성

- RESTful: Spring Boot로 `/hello`, `/users/{id}` 제공
- RPC: HTTP 위에 RPC 스타일 엔드포인트(예: `/rpc/add`) 예제 제공
- gRPC: `Greeter/SayHello` proto + 서버/클라이언트 예제 제공
